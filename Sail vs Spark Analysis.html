Sail vs Spark Analysis
Performance Investigation · pysail 0.7.2 vs Spark 4.2.0

Why Sail Is Faster Than Spark on Parquet

54.88M rows · 9.71 GB · 2 Parquet files · Apple M1 · 10-run medians  ·  Sail pysail 0.7.2 · SAIL_MODE=local-cluster · 3 Tokio threads · 1 Rust process  vs  Spark 4.2.0 · local-cluster[3,1,1024] · 1 driver + 3 executor JVMs
Dataset: FRTB SA capital output. Two Parquet files (parquet1.parquet: 27.37M rows, 4.84 GB, 56 row groups  ·  parquet2.parquet: 27.51M rows, 4.87 GB, 57 row groups) combined via a SQL view. 32 columns: trade identifiers (cobdate, node_id, legal_entity_group_id, correlation_scenario_id, driving_scenario) plus per-asset-class capital doubles (commodities, equities, interest rates, FX, credit — delta/vega/curvature each) and summary columns (total, rrao).

Sail's claims

What Sail claims about its performance advantage

Before running experiments, these are the performance claims made by Sail (pysail 0.7.2, backed by DataFusion/Apache Arrow):

Single-process architecture — no inter-process coordination or JVM executor RPC
LLVM-compiled Arrow compute operators — not interpreted row-by-row
No JVM GC pauses — Rust RAII eliminates stop-the-world overhead
Parquet statistics and metadata pushdown — skip I/O where possible
Columnar memory end-to-end — Arrow format throughout, no row conversion
SIMD vectorization — Rust/LLVM exploit CPU vector units

We ran targeted experiments against the actual Spark and Sail execution plans and event logs to test each claim. Here is what the measurements showed.

§2 · Finding 1

Sail's single-process architecture eliminates the RPC and serialization overhead that Spark's multi-JVM cluster model incurs

Both engines read Parquet with vectorized columnar scans — Spark physical plans show Batched: true. The performance gap comes from how they dispatch work. Spark local-cluster is four JVM processes (driver + 3 executors) connected via Netty RPC. Reading 54.88M rows creates 74 tasks — one per Parquet row group — each serialized by the driver, scheduled via Netty, executed by an executor, and the result returned. Sail runs 3 Tokio async threads inside a single Rust process. No IPC, no serialization.

§3 · Finding 2

Spark processes rows one at a time through virtual dispatch; Sail runs LLVM-compiled columnar kernels

WholeStageCodeGen (WSCG) is Spark's operator-fusion optimization: it compiles multiple operators (scan + filter + aggregate) into a single JIT-compiled code stub that processes rows in a tight loop, eliminating the Volcano iterator overhead. Without it, every row passes through a chain of operator.next() virtual calls — interpreted execution.

We ran df.explain("codegen"), df.explain("extended") and df.explain(True) on Spark 4.2.0 local-cluster[3,1,1024] for three FRTB queries. All three forms returned the same result:

§4 · Finding 3

JVM GC overhead: confirmed minor by three independent measurements

Earlier analysis declared GC unmeasured. We ran three independent experiments to close this gap. All three converge on the same conclusion: GC is real but contributes less than 3% of wall-clock time per query and is not a primary cause of Spark's slowness. Sail has zero GC overhead — Rust uses RAII (ownership/borrowing), with memory freed at compile-time-determined drop points.

Measurement 1 — Spark event log (JVM GC Time per task)

Parsed the Spark event log from the main 10-run benchmark (273 stages, 267 jobs, 3.9 MB zstd). Every SparkListenerTaskEnd event carries a JVM GC Time field from the JVM's GarbageCollectorMXBeans. This is cumulative GC time reported per task.

Measurement 3 — Heap size variation (experimental validation)

If GC were a significant factor, halving the executor heap should force more frequent GC cycles and measurably degrade performance. We ran 512m vs 1g (baseline). 256m and 2g both hit system memory limits on this machine and could not complete.

Query512m executor1g executor (baseline)Change
full_agg 4,824ms 4,946ms −2.5% (within noise)

Performance does not degrade when the heap is halved. The 512m results are similar to or faster than 1g — G1GC performs efficiently at smaller heap sizes for these short-lived allocation patterns. This confirms that GC is not a wall-time sensitivity factor for these queries.

Sail GC overhead: zero. Rust uses ownership and borrowing — memory is freed at compile-time-determined drop points (RAII). There is no garbage collector, no stop-the-world pause, and no GC tuning required. For Spark, GC is a one-sided tax: 1.2–4.6% of executor time on these queries, rising under larger working sets or longer runs.
§5 · Finding 4

COUNT(*): Sail reads zero bytes from the Parquet footer; Spark reads every row

Parquet files store the total row count in the file footer at creation time. Sail reads this at planning time and substitutes it as a constant — no data is read. Spark 4.x does not use this optimization by default (spark.sql.parquet.aggregatePushdown is off).

Appendix · Measurement Methodology

How every number was obtained

Wall-clock times — measured in Python client, from query submission to result received. Includes ~182ms SparkConnect gRPC overhead for Sail (plan compilation + serialization per query — confirmed from compute_only_inmem: Sail engine 314ms, pysail wall 496ms). Reported speedups therefore understate the raw Sail vs Spark execution gap. 1 warmup run (discarded) + 10 timed runs for main queries, 5 for isolation queries. Medians reported.

Spark event log (GC Measurement 1) — zstd-compressed eventlog_v2_app-20261015163711 (3.9 MB). Parsed 273 stages, 267 jobs. Per-stage GC from JVM GC Time in SparkListenerTaskEnd.Task Metrics. Queries identified by (bytes_read_MB, shuffle_write_KB) signature.

Per-executor STW pause log (GC Measurement 2) — fixed executor GC log using -Xlog:gc*:file=gc_exec_%p.log:time,uptime,tags. Three separate files captured (one per executor JVM process). Parsed with Pause regex. 4 queries × (1 warmup + 5 runs) = 24 runs. JDK 17.0.11.

Heap variation (GC Measurement 3) — gc_option2_heap_variation.py ran the same 3 queries at executor.memory=512m and 1g (3 timed runs + 1 warmup each). Fresh SparkSession per heap size. 256m and 2g failed due to system memory constraints.

WholeStageCodeGen — verified via df.explain("codegen"), df.explain("extended"), df.explain(True) on Spark 4.2.0 local-cluster[3,1,1024] for scan_only_sum1col, full_agg, filtered_agg. All three forms returned "Found 0 WholeStageCodegen subtrees".

DataFusion operator times — from EXPLAIN ANALYZE via pysail. Elapsed times are cumulative across partitions (3 workers). Not wall-clock query time.

local_vs_cluster.json — Spark local[3] vs local-cluster[3,1,1024], same machine, same data, 5-run medians. Quantifies Netty RPC + JVM process coordination overhead.

Cluster config (both engines) — Sail: SAIL_MODE=local-cluster, 3 Tokio workers, 1 Rust process. Spark: local-cluster[3,1,1024] (3 executors × 1 core × 1024 MB), AQE=true, filterPushdown=true, shuffle.partitions=3.
